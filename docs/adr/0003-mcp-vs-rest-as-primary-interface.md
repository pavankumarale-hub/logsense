# ADR 0003 — MCP as Primary Interface, REST as Secondary

**Status:** Accepted
**Date:** 2024-01-15
**Deciders:** Project author

---

## Context

LogSense exposes its core functions (`ingest_logs`, `get_clusters`,
`get_rca_for_cluster`, `draft_incident_report`) through two interfaces:

- **MCP (Model Context Protocol)** — used by Claude Desktop, Claude Code,
  and any MCP-compatible client
- **REST (FastAPI)** — used by curl, dashboards, CI scripts, non-MCP clients

The question is which interface is the "primary" one that drives design
decisions, and why.

---

## Decision

**MCP is the primary interface.** REST mirrors it for compatibility.

---

## What "primary" means here

- The tool signatures (names, parameters, descriptions) are defined in
  `mcp_server/server.py` first.
- The REST routes in `api/routes/` are written to exactly mirror those
  signatures.
- Documentation, the demo script, and the README lead with MCP usage.
- When there is a design tension (e.g. async vs sync, return format), we
  resolve it in favor of MCP's constraints.

---

## Rationale

### The MCP value proposition

An LLM-native pipeline should be callable from within an LLM reasoning loop
without any human glue code. MCP makes this possible:

```
User → Claude Desktop → LogSense MCP tool → Result back to Claude → Next reasoning step
```

Without MCP, the workflow requires a human to:
1. Copy-paste log content
2. Call the API manually
3. Feed the RCA result back to the LLM

With MCP, Claude can autonomously ingest logs, request triage, run RCA, and
propose a draft issue — all within a single conversation turn.

This is precisely the class of system we build in production: **AI agents
that close the loop** rather than producing reports that sit in dashboards.

### Why not REST-first?

REST is more universally understood. But:

1. REST clients treat LogSense as a passive API. MCP clients treat it as a
   tool the LLM can *decide to use* within a reasoning chain. The second is
   architecturally richer and demonstrates a different class of capability.
2. For a portfolio project aimed at demonstrating AI/agent engineering ability,
   shipping a working MCP server is a stronger signal than shipping another
   CRUD API.
3. The implementation cost of wrapping functions in MCP is low (FastMCP's
   `@mcp.tool()` decorator). The REST layer is then generated by mirroring
   those same functions.

### Why not MCP-only?

REST is kept as a first-class interface because:

1. Not every user has Claude Desktop configured with an MCP server.
2. CI pipelines, shell scripts, and external monitoring tools speak HTTP.
3. The FastAPI `/docs` page provides interactive exploration that helps
   evaluators understand the API surface without installing anything.

---

## Consequences

- `logsense.mcp_server.server` is the source of truth for tool signatures.
- REST routes duplicate some logic — this is acceptable because it is
  intentional mirroring, not accidental duplication.
- MCP stdio transport is used (vs HTTP transport) because it is the default
  for Claude Desktop and requires no port configuration.
- The `logsense-mcp` command (`python -m logsense.mcp_server.server`) is
  the intended entry point for MCP clients; `logsense serve` starts REST.
